# Recipe generation latency: primary-source research

Date: 2026-11-04. Builds on #41 (batch 5, refill at unseen <= 5, eager second batch, 6-run cap, NN/g limits, Instagram prefetch, Home Mixer dedup). This doc does not repeat #41 and does not propose an architecture.

Measurement baseline (probe, same 6-item inventory, batch ceiling 5): default thinking spends 4.4-4.6K hidden thinking tokens, first byte at 23.5 s, 27-28 s total, 2 recipes. `thinking_level=LOW`: first byte 1.1 s, 4.0 s total, 1 recipe. Output streams at ~200-250 tokens/s and a recipe is ~500-750 tokens, so each extra recipe adds roughly 2-3.5 s.

Note: Google's Gemini API docs moved. `ai.google.dev/gemini-api/docs/*` now 301-redirects to `aistudio.google.com/docs/*`. Links below point to the new location.

## Summary

- **Thinking is the main lever, and our model's default is "medium", not off.** Gemini 3.6 Flash supports `minimal`, `low`, `medium`, `high`. Its default is `medium`. Docs say to lower `thinking_level` to cut latency ([thinking docs](https://aistudio.google.com/docs/thinking), [Gemini 3.6 notes](https://aistudio.google.com/docs/whats-new-gemini-3.6)). Thinking tokens are billed as output and count toward `max_output_tokens`.
- **Gemini 3.6 Flash is now labeled "previous-generation".** The newest Flash, 3.8, has no `minimal` level ([models](https://aistudio.google.com/docs/models), [thinking docs](https://aistudio.google.com/docs/thinking)). Any thinking-level decision should note this migration risk.
- **Production food/commerce teams keep the LLM off the request path.** DoorDash generates carousels offline and serves them from a vector index. Instacart caches LLM-generated placements and search content. Yelp precomputes LLM output for frequent "head" queries. Pinterest distills an LLM into a fast model ([DoorDash](https://careersatdoordash.com/blog/doordash-offline-llms-online-personalization-generating-carousels/), [Instacart](https://tech.instacart.com/supercharging-discovery-in-search-with-llms-556c585d4720), [Yelp](https://engineeringblog.yelp.com/2025/02/search-query-understanding-with-LLMs.html), [Pinterest](https://arxiv.org/abs/2410.17152)). FreshPlate is unusual because its input (a private inventory) has no shared "head" to precompute.
- **Streaming is the vendors' top technique for perceived latency.** OpenAI calls "make your users wait less" the single most effective approach ([OpenAI latency guide](https://developers.openai.com/api/docs/guides/latency-optimization)). Gemini streams structured output as valid partial JSON chunks ([structured output](https://aistudio.google.com/docs/structured-output)). That means the first recipe can be parsed before the fifth is written.
- **Streaming does not remove thinking time.** Hidden reasoning finishes before the first visible byte. With default thinking, our first byte was at 23.5 s, so streaming alone would still show the first card after 24 s or more.
- **Parallel calls trade quota and cost for wall-clock time.** OpenAI and Anthropic document parallel fan-out and running checks in parallel ([OpenAI](https://developers.openai.com/api/docs/guides/latency-optimization), [Anthropic](https://www.anthropic.com/engineering/building-effective-agents)). Each extra call counts against per-project RPM/RPD limits ([rate limits](https://aistudio.google.com/docs/rate-limits)).
- **Quality checks move off the critical path by splitting checks into tiers.** Cheap deterministic gates stay inline. Model-based judges run in parallel, after serving, or offline on samples. DoorDash and Instacart both describe this layering ([DoorDash via ZenML, secondary](https://www.zenml.io/llmops-database/offline-llm-generation-for-hyper-personalized-carousel-recommendations), [Instacart via sysdesign-wiki, secondary](https://sysdesign-wiki.pages.dev/sources/2026-02-26-instacart-our-early-journey-to-transform-discovery-recommendations-with-llms/)).

## 1. How production LLM recommendation systems are architected

**Two-stage retrieve-then-rank.** A recommender first pulls a few hundred plausible candidates out of millions cheaply (retrieval), then scores those few carefully (ranking). YouTube's 2016 paper is the standard reference. It describes a separate candidate generation model and a separate ranking model ([Covington et al., RecSys 2016](https://research.google/pubs/deep-neural-networks-for-youtube-recommendations/)).

**Two-tower retrieval.** A "two-tower" model has two neural networks. One turns the user or query into a vector, and the other turns each item into a vector. Retrieval then becomes a nearest-neighbor search between the vectors. Item vectors can be precomputed and indexed, which makes retrieval fast. Google used this for YouTube retrieval over "tens of millions" of videos ([Yi et al., RecSys 2019](https://research.google/pubs/sampling-bias-corrected-neural-modeling-for-large-corpus-item-recommendations/)). FreshPlate's retrieve step is a simple form of this: one Gemini embedding for the inventory query, compared against precomputed Food.com recipe embeddings in pgvector.

**Where the LLM sits.** Published production systems keep the LLM out of the synchronous path. They use one of three patterns:

| Pattern | What it means | Example |
|---|---|---|
| Offline generator | The LLM writes content in batch. Serving reads stored results. | DoorDash generates personalized carousels offline from consumer "memory blocks". It stores them in Milvus and a metadata store, and serves them with online vector retrieval ([DoorDash, 2026](https://careersatdoordash.com/blog/doordash-offline-llms-online-personalization-generating-carousels/); primary page blocked our fetcher, details from [ZenML summary, secondary](https://www.zenml.io/llmops-database/offline-llm-generation-for-hyper-personalized-carousel-recommendations)). Instacart's 2024 search discovery runs a batch job and stores responses in a key-value store keyed by query. Freshness is limited to daily ([Instacart, 2024](https://tech.instacart.com/supercharging-discovery-in-search-with-llms-556c585d4720); details via [ZenML, secondary](https://www.zenml.io/llmops-database/using-llms-to-enhance-search-discovery-and-recommendations)). |
| Head cache + tail fallback | Precompute LLM output for frequent inputs. Use a cheaper path for rare inputs. | Yelp precomputes high-end LLM output for head queries because query frequency "follows the power law". It precomputed review-highlight expansions for 95% of traffic and used heuristics for the rest ([Yelp, Feb 2025](https://engineeringblog.yelp.com/2025/02/search-query-understanding-with-LLMs.html)). |
| Teacher-student distillation | A large LLM labels data, and a small fast model learns to imitate it and serves live. | Pinterest distills an LLM relevance model into "real-time servable" models ([Pinterest, CIKM 2024 workshop](https://arxiv.org/abs/2410.17152)). Instacart's Shopping Hub fine-tunes open-weight students on teacher output to meet latency and cost limits ([Instacart, 2026-02-26](https://company.instacart.com/tech-innovation/our-early-journey-to-transform-instacart-s-discovery-recommendations-with-llms); primary blocked, details via [sysdesign-wiki, secondary](https://sysdesign-wiki.pages.dev/sources/2026-02-26-instacart-our-early-journey-to-transform-discovery-recommendations-with-llms/)). |

The academic surveys say the same. The 2024-25 LLM-enhanced recommender survey describes a field shift toward "avoiding their use during inference" because of latency and memory costs ([Liu et al., arXiv 2412.13432](https://arxiv.org/abs/2412.13432)). A late-2025 generative recommendation survey names inference latency as a core deployment obstacle ([arXiv 2510.27157](https://arxiv.org/abs/2510.27157); search-snippet level only, unverified in full text).

**Food/recipe specifics.** Samsung Food (built on Whisk) has no public engineering write-up. Launch coverage describes "Personalize Recipe" features only ([Samsung newsroom](https://news.samsung.com/us/?p=36356); architecture unverified). An Instacart engineering-manager talk says Instacart generates recipes from top search keywords, offline ([Luma listing, secondary, unverified](https://luma.com/data-phoenix-tech-talks-su26-9)). I found no primary source for a system that generates full recipes live from a private inventory. FreshPlate's input is per-user and changes often, so the "head cache" pattern applies only weakly (see open questions).

## 2. Latency techniques: what each buys and costs

**Thinking budget.** "Thinking" means the model writes hidden reasoning tokens before its answer. Those tokens take generation time and you pay for them, but the user never sees them. Current Gemini docs ([thinking](https://aistudio.google.com/docs/thinking)):
- Use `thinking_level` (`thinking_budget` is gone from the page). The 3.6 notes say to replace `thinking_budget` with `thinking_level` ([3.6 notes](https://aistudio.google.com/docs/whats-new-gemini-3.6)).
- Supported levels for `gemini-3.6-flash`: minimal, low, medium, high. Default: medium. `gemini-3.8-flash`: low, medium, high (no minimal). `gemini-3.5-flash-lite`: default minimal.
- The docs don't say whether thinking can be fully disabled on Gemini 3 models. Treat "off" as unavailable.
- Thinking tokens count toward `max_output_tokens`. A run that hits the cap mid-thought returns "incomplete" and is still billed.
- Docs advise lowering the level, not shrinking `max_output_tokens`, to cut latency, and suggest minimal for simple tasks.
- LinkedIn reported the same cost of chain-of-thought: the extra tokens are ones "the member never sees" but still wait on ([LinkedIn Engineering, Apr 2024](https://www.linkedin.com/blog/engineering/generative-ai/musings-on-building-a-generative-ai-product)).

What it buys for us: 23.5 s to 1.1 s first byte (measured). Cost: our probe returned 1 recipe instead of 2-5 at LOW/MINIMAL. Whether that is a thinking effect or a prompt/schema effect is unknown.

**Generate fewer tokens.** OpenAI's guide says cutting 50% of output tokens "may cut ~50%" of latency ([OpenAI](https://developers.openai.com/api/docs/guides/latency-optimization)). Anthropic gives the same advice and warns that `max_tokens` truncates mid-sentence ([Anthropic reduce latency](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-latency)). LinkedIn switched from JSON to YAML because it is "less verbose". It also built a defensive parser to avoid re-prompting on the ~10% of malformed outputs ([LinkedIn](https://www.linkedin.com/blog/engineering/generative-ai/musings-on-building-a-generative-ai-product)). For us, shorter step text or fewer steps would cut the per-recipe ~2-3.5 s.

**Structured output cost.** Gemini rejects overly complex schemas with 400 errors. It does not enforce `minLength`/`maxLength`, so the app must validate values ([structured output](https://aistudio.google.com/docs/structured-output)). Google does not document a latency cost. OpenAI documents extra latency only on the first request with a new schema ([OpenAI structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs)). Whether Gemini has a similar first-schema cost is unverified.

**Streaming and emitting the first item early.** Streaming sends tokens as they are generated instead of waiting for the full response. Gemini's streamed structured output arrives as partial JSON chunks that concatenate into the final object ([structured output](https://aistudio.google.com/docs/structured-output)). The Vercel AI SDK shows the "first item early" pattern: its `elementStream` emits each array element once it is complete and schema-validated ([AI SDK docs](https://ai-sdk.dev/docs/ai-sdk-core/generating-structured-data)). LinkedIn streams every request and fires downstream calls as soon as their parameters are parsed ([LinkedIn](https://www.linkedin.com/blog/engineering/generative-ai/musings-on-building-a-generative-ai-product)). Streaming between the server and Gemini doesn't break the "no client streaming" decision. The server could close recipe 1, check it, and hold it, while the session endpoint still returns one response.

**One-at-a-time vs batch.** One big call pays the thinking and first-byte overhead once, but the client waits for every recipe. Single-recipe calls pay the overhead each time, but recipe 1 is ready sooner. OpenAI's guide covers both directions: combine steps to cut request count, or split them so a faster model handles part of the work. It says to choose by testing ([OpenAI](https://developers.openai.com/api/docs/guides/latency-optimization)).

**Parallel fan-out.** Run independent calls at the same time: "Two shirts take just as long to dry as one" ([OpenAI](https://developers.openai.com/api/docs/guides/latency-optimization)). Anthropic calls this "sectioning" ([Anthropic, Dec 2024](https://www.anthropic.com/engineering/building-effective-agents)). Costs:
- Every call is one request against per-project RPM/RPD, and the prompt input is re-billed each time ([rate limits](https://aistudio.google.com/docs/rate-limits)).
- Parallel calls can't see each other's output, so duplicate recipes are possible (#41's dedup filter becomes load-bearing).
- Tier 1 billing (per memory) relaxes the quota concern from #41. The real RPM must still be read in AI Studio.

**Speculative execution.** Start the likely next step before you know you need it, and cancel it if the guess was wrong ([OpenAI](https://developers.openai.com/api/docs/guides/latency-optimization)). For us: start the next generation before the judge finishes, and drop it if the judge passes. #41's eager second batch already applies this at the feed level.

**Precomputation and caching.**
- *Exact-key precompute.* Generate ahead of time, keyed by input. This is what DoorDash, Instacart, and Yelp do (section 1). For FreshPlate the key would be an inventory signature, such as a hash of the sorted item ids. Hits come from the same user with an unchanged inventory. A shared cache across users is unlikely to help because inventories differ (unverified, no data).
- *Semantic caching.* Embed the request and return a cached answer for a "close enough" previous request. GPTCache documents this and warns of false positives on hits ([GPTCache README](https://github.com/zilliztech/GPTCache)). For grounding this is risky: a near-match inventory may lack an ingredient the cached recipe uses. Every cache hit would need the grounding check rerun.
- *Gemini implicit caching.* This is on by default for 2.5+ models. It needs at least 4,096 prompt tokens on 3.6 Flash, so put stable content first ([caching](https://aistudio.google.com/docs/caching)). Docs describe cost savings only and say nothing about latency. Our prompt size versus the 4,096 minimum is unverified.
- *Background precompute tiers.* Batch and Flex are 50% off but take minutes to hours. Use them only for off-path work such as nightly evals ([priority inference table](https://aistudio.google.com/docs/priority-inference), [batch](https://aistudio.google.com/docs/batch-api)).

**Priority inference.** Priority inference is a preview tier with "second response times". It costs 75-100% more and supports 3.6 Flash ([priority inference](https://aistudio.google.com/docs/priority-inference)). It reduces queueing, not thinking, and its effect on our numbers is unmeasured.

**Smaller model per step.** OpenAI says smaller models "usually run faster (and cheaper)" ([OpenAI](https://developers.openai.com/api/docs/guides/latency-optimization)). Its guardrails cookbook uses a smaller model for the topical guardrail ([OpenAI cookbook](https://developers.openai.com/cookbook/examples/how_to_use_guardrails)). Gemini 3.5 Flash-Lite is the "fastest, most cost-effective 3.5 model", defaults to minimal thinking, and lists classification and structured parsing as use cases ([models](https://aistudio.google.com/docs/models), [3.6 notes](https://aistudio.google.com/docs/whats-new-gemini-3.6)). That fits the `assess_meals` judge. Our CLAUDE.md allows only `gemini-3.6-flash`, so this needs an explicit decision.

## 3. Keeping time-to-first-item low in AI-content feeds

- **Show partial results before the full batch is done.** Vendors list streaming, chunking, progress indicators, and loading states under "make users wait less" ([OpenAI](https://developers.openai.com/api/docs/guides/latency-optimization), [Anthropic](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-latency)). #41 already covered NN/g's skeleton (2-10 s) and progress-bar (10 s+) guidance.
- **Serve the first item from a fast path.** The Yelp head cache and DoorDash index are fast paths, and the LLM only fills the store ([Yelp](https://engineeringblog.yelp.com/2025/02/search-query-understanding-with-LLMs.html), [DoorDash](https://careersatdoordash.com/blog/doordash-offline-llms-online-personalization-generating-carousels/)). FreshPlate's possible fast paths are a cached last session for an unchanged inventory, or the first streamed recipe.
- **Generate the rest behind the first item.** This is #41's eager refill, applied inside the first page: return card 1 (or 1-2) as soon as it is ready, and let a background run fill cards 2-5. I found no primary source that publishes a time-to-first-item number for an LLM recommendation feed. That gap remains unverified.

## 4. Keeping quality guarantees off the synchronous path

- **Split checks by cost.** DoorDash runs deterministic gates before storage: confidence thresholds, minimum counts, and dedup. Rule-based evaluators run next, and LLM-as-judge rubrics run on stratified samples with launch thresholds. The model can also abstain when evidence is thin ([ZenML summary of DoorDash, secondary](https://www.zenml.io/llmops-database/offline-llm-generation-for-hyper-personalized-carousel-recommendations)). Instacart uses embedding dedup, an LLM judge on a small share of users, and a fine-tuned DeBERTa cross-encoder at over 99% lower cost than the LLM ([sysdesign-wiki, secondary](https://sysdesign-wiki.pages.dev/sources/2026-02-26-instacart-our-early-journey-to-transform-discovery-recommendations-with-llms/)).
- **Run checks in parallel with generation, and cancel on failure.** Anthropic found a separate guardrail call works better than one call doing both jobs ([Anthropic](https://www.anthropic.com/engineering/building-effective-agents)). OpenAI's cookbook runs input guardrails alongside the main call. Its output moderation runs after the response, so it adds latency ([OpenAI cookbook](https://developers.openai.com/cookbook/examples/how_to_use_guardrails)).
- **Judge-after-serve is a policy choice.** An item can be shown and pulled later, or held until checked. None of the sources describe pulling an item a user has already seen. DoorDash and Instacart avoid the question by judging before the item reaches the store.
- **Implication for FreshPlate (no recommendation).** Inventory grounding is deterministic and takes milliseconds, so it can stay inline on every card. The `assess_meals` LLM judge (~1.2 s) is the part that could move. Options: run it per recipe as each one streams in, run it on a faster model, or run it async and swap out failures before the user scrolls to them.
- **Offline evals keep the guarantee measurable.** LinkedIn's automatic evaluation was "still a work in progress", so it relied on human annotation ([LinkedIn](https://www.linkedin.com/blog/engineering/generative-ai/musings-on-building-a-generative-ai-product)). FreshPlate's existing eval suite (`docs/evals.md`) can cover this offline.

## Technique menu for FreshPlate

Effects are estimates from today's measurements (first byte 23.5 s default / 1.1 s LOW, ~200-250 tok/s, ~500-750 tokens per recipe, retrieval ~1 s, judge ~1.2 s). They are not new measurements.

| Technique | What it does | Expected effect on time-to-first-card | Cost / risk | Sources |
|---|---|---|---|---|
| Lower `thinking_level` (low/minimal) | Less hidden reasoning before output | ~28 s to ~5-6 s graph (measured) | Probe returned 1 recipe, quality unproven; 3.8 Flash drops `minimal` | [thinking](https://aistudio.google.com/docs/thinking) |
| Trim output (fewer or shorter steps, terser fields) | Fewer tokens to stream | ~0.5-1.5 s saved per recipe | Less detailed recipe; rubric may penalize it | [OpenAI](https://developers.openai.com/api/docs/guides/latency-optimization), [LinkedIn](https://www.linkedin.com/blog/engineering/generative-ai/musings-on-building-a-generative-ai-product) |
| Server-side stream + parse first recipe | Close recipe 1 as soon as its JSON object completes | At LOW: ~1 s retrieval + ~1.1 s first byte + ~2-3.5 s = ~4-6 s to card 1. At default: still ~26 s | More parser code; partial-JSON edge cases; client contract decision | [structured output](https://aistudio.google.com/docs/structured-output), [AI SDK](https://ai-sdk.dev/docs/ai-sdk-core/generating-structured-data) |
| Parallel single-recipe calls | N calls at once, one recipe each | ~one-recipe latency for all N (~4-5 s at LOW) | N times RPM and input tokens; cross-call duplicates; diversity harder | [OpenAI](https://developers.openai.com/api/docs/guides/latency-optimization), [rate limits](https://aistudio.google.com/docs/rate-limits) |
| Return first 1-2 cards, background-fill the rest | Shrink the synchronous batch | Roughly halves the generate step | Extra request; feed contract change; builds on #41 refill | #41, [OpenAI](https://developers.openai.com/api/docs/guides/latency-optimization) |
| Judge async / per item / in parallel | Take `assess_meals` (~1.2 s) off the wait | -1.2 s, or overlap with generation | Bad card may show briefly, or a swap is needed; retry loop gets harder | [Anthropic](https://www.anthropic.com/engineering/building-effective-agents), [OpenAI cookbook](https://developers.openai.com/cookbook/examples/how_to_use_guardrails) |
| Flash-Lite for judge | Faster, cheaper model for classification | Likely under 1.2 s (unmeasured) | Breaks the "only 3.6 Flash" rule; judge accuracy must be re-evaluated | [models](https://aistudio.google.com/docs/models) |
| Cache by inventory signature | Reuse the last session for an unchanged inventory | ~0 s on hit | Stale or repeat content; hit rate unknown; must invalidate on inventory edit | [Yelp](https://engineeringblog.yelp.com/2025/02/search-query-understanding-with-LLMs.html), [Instacart](https://tech.instacart.com/supercharging-discovery-in-search-with-llms-556c585d4720) |
| Semantic cache | Reuse for similar inventories | ~0 s on hit | False hits break grounding; needs re-check | [GPTCache](https://github.com/zilliztech/GPTCache) |
| Precompute on inventory change | Generate in background when the pantry changes | ~0 s at open, if finished | Spend on sessions never opened; quota | [DoorDash](https://careersatdoordash.com/blog/doordash-offline-llms-online-personalization-generating-carousels/) |
| Implicit context caching | Discount on a repeated prompt prefix | None documented | Needs ≥4,096-token prefix | [caching](https://aistudio.google.com/docs/caching) |
| Priority inference | Higher-priority serving tier | Unknown; cuts queueing only | +75-100% price; preview | [priority](https://aistudio.google.com/docs/priority-inference) |

## Open questions

1. Is "1 recipe at LOW/MINIMAL" caused by thinking level, or by the prompt/schema (for example, the model stops early without planning)? It needs a controlled probe across several inventories before a thinking level can be chosen.
2. How much does thinking vary with inventory complexity at LOW? One inventory is not enough to set a budget.
3. Does Gemini add first-request latency for a new response schema, as OpenAI does? Unverified.
4. How large is our generate prompt? This decides whether implicit caching (≥4,096 tokens) applies.
5. What are the real Tier 1 RPM/RPD for `gemini-3.6-flash`? The docs publish none ([rate limits](https://aistudio.google.com/docs/rate-limits)). Parallel fan-out depends on this.
6. Should the model rule allow Flash-Lite for the judge, and should we plan a migration to 3.8 Flash, which has no `minimal`?
7. When should a card be judged: hold until checked, or show then swap? No primary source covers retracting an already-shown item.
